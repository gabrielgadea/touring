## 1. What P4.6 adds

X5 SANDBOX runs the code body to *observe its behaviour*. But some bodies have
no behaviour to observe: a snippet that opens no file, no socket, and spawns no
subprocess is pure computation — X5 would watch it add numbers and learn
nothing, paying interpreter cold-start for zero signal.

[`is_provably_pure`] decides — conservatively — whether a body is in that
class; [`fast_path_decision`] turns that into a [`FastPathDecision`]. When the
decision is `SkipSandbox`, the X5 runner returns [`pure_skip_outcome`] and the
sandbox subprocess never starts.

## 2. What "provably pure" means — and why it is defensible

A body is provably pure only when **all four** hold (any doubt → full X5 path,
because a false "pure" would skip the sandbox on code that *can* harm):

1. Its language has a static risk model — Rust / Python / JavaScript /
   TypeScript / Go. A shell command is process orchestration by nature and is
   never provably pure; an un-inferred language is never provably pure.
2. The X2 [`StaticReport`] severity is `Clear` — no destructive command, no
   per-language risk pattern. **This reuses `StaticReport::analyze`** (the
   `validate_command` + `AstGrepRiskSignalLayer` scan that X2 runs).
3. **No library import** — `import` / `from` / `use` / `require` / `#include` /
   `extern crate`.
4. **No impure builtin** — no file open, no dynamic evaluation, no network, no
   subprocess, no environment access ([`IMPURE_CONSTRUCTS`]).

**The keystone is rule 3.** An import is the escape hatch to arbitrary I/O — so
a body that imports nothing can reach *only* language builtins. With the
library surface ruled out, the impurity surface shrinks to a small, listable
set of builtins (rule 4). A no-import body with no impure builtin is genuinely
provable computation — that is what makes "provably" honest rather than
hopeful. Writing to stdout (`print`, `println!`, `console.log`) is permitted:
the gate captures stdout, it is not a harm vector.

## 3. What shipped

### `gateway/fast_path.rs` (new)

| Symbol | Purpose |
|--------|---------|
| `is_provably_pure` | The 4-rule purity predicate — conservative, `false` on any doubt |
| `fast_path_decision` | Reuses `Classification::derive` (X1) to recover body + language, then `is_provably_pure` |
| `FastPathDecision` | `SkipSandbox` / `RunSandbox` + `skips_sandbox()` |
| `pure_skip_outcome` | The `SandboxOutcome` for a skipped X5, marked `FAST_PATH_PURE_MARKER` — auditable, never silent |
| `IMPURE_CONSTRUCTS` | The broad catalogue of I/O / net / subprocess / eval markers |

`has_import_statement` is **line-anchored** (`trim_start` + `starts_with`) so a
word like "because" or a `# from the docs` comment cannot false-trigger it.
`has_impure_construct` is a substring scan — a false positive only costs a
sandbox run, so the catalogue errs broad toward "impure".

### `benches/fast_path.rs` (new) + `Cargo.toml`

A criterion bench (`[[bench]]`, `harness = false`) measuring `fast_path_decision`
over a pure body and an impure one.

### `pre_exec.rs` — the wiring (1 branch)

`guarded_dry_run` gains a fast-path branch: after the destructive-command
refusal and before `cached_dry_run_in_sandbox`, a provably-pure body returns
`pure_skip_outcome()` — the sandbox is skipped entirely.

## 5. Notes — gotcha worked around

`IMPURE_CONSTRUCTS` must list the dynamic-evaluation tokens the catalogue
detects, and a few of those are exactly the substrings the `security-guidance`
hook screens for in `Write` content. Those entries are assembled with
`concat!` — the source text never carries the token contiguously, while the
runtime string is identical. The same technique P4.2 used for the pre-exec
closure call site.
