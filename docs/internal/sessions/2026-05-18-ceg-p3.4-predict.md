## 1. What P3.4 adds

X4 PREDICT (`gateway/predict.rs`) is the gateway's speculative check. *Before*
the real sandbox runs the code (X5), X4 predicts the probability that the run
will succeed, from the RL outcome history of similar past executions — so the
later DECISION stage (X7) can weigh "this looks risky" without spending a
sandbox run.

## 3. What shipped — `gateway/predict.rs`

| Symbol | Purpose |
|--------|---------|
| `OutcomeStats` | Observed `successes` / `failures` for a signature |
| `PredictionConfidence` | `None` / `Low` / `Medium` / `High` — by sample size |
| `ExecutionOutcomePredictor` | Laplace-smoothed Beta estimator |
| `PredictionReport` | `signature` + `success_probability` + `observed` + `confidence` |
| `signature_for` | Reduces a `RawInvocation` to its `ActionSignature` |
| `Execution::<Verified>::predict` | The X3→X4 transition to `Predicted` |

**The estimator.** `success_probability = (s + α) / (s + f + 2α)` — a
Beta(α, α) Laplace smoothing. The default `α = 1` is a uniform prior, so an
unseen signature predicts the neutral `0.5`; 100 successes / 0 failures
predicts `> 0.95` without ever claiming a false `1.0`. The `α = 0` + no-history
case (a genuine `0/0`) is guarded — it returns `0.5` rather than a `NaN`.

**Signature reuse.** `signature_for` reduces the captured call to an
`ActionSignature` via the in-repo `ActionSignature::from_pre_tool`; its
`to_key()` (`outcome:<tool_class>:<intent_class>:<qualifier>`) is the *same*
key under which the X9 LEARN stage will store the eventual outcome — so the
prediction loop closes on a single agreed key.

**Closure-driven.** `predict<F: Fn(&str) -> OutcomeStats>` injects the outcome
history, so the transition stays pure and unit-testable — consistent with X3's
design. P3.7 backs the closure with the touring memory `outcome:*` ledger.

## 4. Typestate extension

`Evidence` gained a `prediction: Option<PredictionReport>` field. Because
`PredictionReport` carries an `f64` probability — for which reflexive equality
does not hold — `Evidence` **drops its `Eq` derive** and keeps `PartialEq`.
This is correct, not a regression: a struct transitively containing a float
should never claim `Eq`. The other report types (`Classification`,
`StaticReport`, `VgpReport`) remain `Eq`. No P3.1–P3.3 test depended on
`Evidence: Eq` — only `PartialEq` (used by `assert_eq!`).
