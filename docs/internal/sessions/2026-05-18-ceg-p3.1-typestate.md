## 1. What P3.1 establishes

P3 builds the unified `X0..X9` Code Execution Gateway. P3.1 lays its spine: a
**typestate** that makes the stage order a compile-time invariant. The gateway
runs every code-bearing tool call through ten ordered stages; the first eight
each produce a distinct state:

| Stage | Name            | State             |
|-------|-----------------|-------------------|
| X0    | CAPTURE         | `Captured`        |
| X1    | CLASSIFY        | `Classified`      |
| X2    | STATIC          | `Analyzed`        |
| X3    | VGP             | `Verified`        |
| X4    | PREDICT         | `Predicted`       |
| X5    | SANDBOX         | `SandboxTested`   |
| X6    | CAPABILITY-GATE | `Gated`           |
| X7    | DECISION        | `Decided`         |

`X8` EXECUTE and `X9` LEARN consume an `Execution<Decided>`; they add no
typestate, so the pipeline has exactly **eight** states — the plan's "8 marker
types".

## 2. The acceptance criterion — and how it is proven

> *Acceptance:* "Compile-time proof that X3 (VGP) and X5 (sandbox) cannot be
> bypassed; mirrors the generator `Draft -> Committed` typestate."

Two mechanisms, both structural:

1. **Sealed linear chain.** `ExecutionState` is a sealed trait (only this
   module's eight markers implement it). The non-terminal seven also implement
   `Advance`, whose associated type `Next` names the *single* successor. The
   only transition, `advance()`, has signature `Execution<S> -> Execution<S::Next>`
   — it moves exactly one stage. There is no method, anywhere, that reaches a
   state two or more hops away. `Predicted` is therefore reachable *only
   through* `Verified` (X3); `Gated` *only through* `SandboxTested` (X5).

2. **`compile_fail` doctests.** Two doctests on `Execution` are *required to
   fail compilation* — `cargo test --doc` verifies they do:
   - skipping to `Verified` in one hop is a type error;
   - `Execution<Decided>` has no `advance` (`Decided` deliberately omits the
     `Advance` impl — terminal).

   These are executable proof artifacts, re-checked on every test run.

This mirrors `touring-generator::executor::typestate` (`Draft -> Verified ->
Rendered -> Speculated -> Committed`): the same sealed-trait + `PhantomData` +
consume-`self` discipline the generator applies to code *generation*, the CEG
now applies to code *execution*.

## 3. What shipped — `crates/touring-hooks/src/gateway/`

100% greenfield: a new `gateway/` module tree. Zero edits to existing code
except one `pub mod gateway;` line in `lib.rs`.

| Symbol | Kind | Purpose |
|--------|------|---------|
| `ExecutionState` | sealed trait | Marker for the 8 states; carries `STAGE` label + `ORDINAL` |
| `Advance` | trait | The 7 non-terminal states' single-successor chain (`Next`) |
| `Captured`..`Decided` | 8 ZST structs | The pipeline states, declared via the `execution_states!` macro |
| `Execution<S>` | struct | The move-only, `#[must_use]` typestate token |
| `Execution::capture` / `advance` | fn | X0 entry constructor / one-stage transition |
| `RawInvocation` | struct | The verbatim X0 capture payload (`tool`, `payload`, `intent`) |
| `ExecutionId` | struct | Deterministic content-addressed id — BLAKE3 over canonical content |
| `Evidence` / `StageRecord` | struct | The append-only per-stage audit ledger (the X9 LEARN trail) |

**Determinism (REGRA #17).** `ExecutionId::derive` is a pure function of
`RawInvocation` content — BLAKE3 over `tool \0 payload \0 intent`, first 64 bits
as lower-hex (`exec-<16 hex>`). No timestamp, address or counter. A `\0`
separator makes `("ab","c")` and `("a","bc")` non-colliding. Equal content →
equal id is what lets `crate::staging` (P1.6) recognise a re-run.

**Design divergence from the generator, documented.** The generator stores each
stage's data *inside* that stage's struct. The CEG typestate is distributed
across files (one module per stage deliverable, P3.2..P3.7), so the 8 states are
ZST markers and per-stage results accumulate in the `Evidence` ledger carried by
every `Execution`. Each transition is the sole constructor of its target state,
so the runtime data-presence invariant holds even though the type tracks only
order.
