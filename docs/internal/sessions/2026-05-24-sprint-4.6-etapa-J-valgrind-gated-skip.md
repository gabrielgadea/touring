## What valgrind would have found (counterfactual)

`valgrind --tool=memcheck` is designed to detect:
- Heap use-after-free / double-free
- Reads from uninitialized memory
- Heap buffer overflows
- Memory leaks
- Invalid free of stack/static pointers

**None** of those are present in this bug. The daemon process exited cleanly
via `process::exit(0)`. Valgrind cannot detect "function I did not mean to call
was called" — that is a logic bug, not a memory bug.

## Cheaper next-line-of-defense (preferred over valgrind)

If memory safety becomes a future concern:

| Tool | Cost | Detects |
|---|---|---|
| `cargo miri test` | seconds (cached) | Undefined behavior in safe Rust; pointer provenance |
| `cargo asan` (AddressSanitizer) | ~2× slowdown | Heap-buffer overflow, use-after-free; runs full test suite |
| `cargo fuzz` (already exists in `fuzz/`) | minutes | Panic / crash on adversarial input |
| Valgrind memcheck | 30× slowdown | Same as ASAN but no compiler instrumentation needed |

Recommendation: if a future signal **does** suggest memcorrupt, prefer
`cargo miri` (instant) → `cargo asan` (small overhead) → valgrind only as last
resort.
