## 1. `ExecSurface` plan-inconsistency analysis + recommendation

### 1.1 Evidence

```
$ touring index find ExecSurface -j
{"count":0,"definitions":[],"symbol_name":"ExecSurface"}

$ grep -rn "ExecSurface" crates/
(zero hits)
```

`ExecSurface` is a **planned** symbol. The plan references it in three places:

| Plan line | Section | Treatment of `ExecSurface` |
|---|---|---|
| `:30` | X1 CLASSIFY narrative | "`ExecSurface` enum" listed as a deliverable concept |
| `:167` | **P1.5** | "New symbols: `ExecSurface::Inferlet`, `ExecSurface::Job`" |
| `:255` | **P3.2** | "New symbols: `ExecSurface`, `CodeBody`, `classify()`" |

P1.5 depends only on `P1.1` (`deps: P1.1`). P3.2 depends on `P3.1,P1.1`. The plan's own phase ordering puts **P1 entirely before P3**. So as written, P1.5 must add `Inferlet`/`Job` variants to an enum that is not defined until two phases later. A wave executing P1.5 would either (a) fail VGP — `ExecSurface` not in index — or (b) be forced to create the enum ad hoc, duplicating P3.2's "New symbols: ExecSurface".

### 1.2 What P1.5 should actually do — recommendation

There is no X0..X9 gateway in Phase 1. P1.5's *acceptance criterion* is the real intent: **"WASM inferlets and background jobs route through the same X0..X9 pipeline as Bash."** That pipeline does not exist until P3. So P1.5 in Phase 1 cannot literally do that either.

**Recommended correction (pick one, ordered by preference):**

**Option A — Re-sequence P1.5 after P3.2 (cleanest).**
Move P1.5 to be a Phase 3 sibling, `deps: P3.2`. Then "New symbols: `ExecSurface::Inferlet`, `ExecSurface::Job`" is coherent: P3.2 creates `enum ExecSurface { Bash, McpCtxExecute, ... }`, and the re-sequenced P1.5 adds the `Inferlet` and `Job` variants + routes `cli_inferlets_exec` / `cli_jobs_spawn` through `classify()` and the gateway. This is the smallest semantic change and keeps P1.5's acceptance criterion literally satisfiable.

**Option B — Keep P1.5 in Phase 1 but rescope it to a coverage audit + wiring-point stub.**
P1.5 (Phase 1) becomes: (1) document the inferlet and job execution entry points (this scout already does most of that); (2) add an `ExecSurface` enum **early** as a minimal 2-variant skeleton (`Inferlet`, `Job`) in a new `gateway/surface.rs`, and have P3.2 *extend* it instead of *create* it (P3.2's "New symbols" line changes from `ExecSurface` to `ExecSurface::Bash, ExecSurface::McpCtxExecute, classify()`); (3) insert a no-op `route_through_gateway()` shim at the two daemon handlers, behind a feature/env flag, that P3 fills in. This keeps P1 self-contained and turns P3.2 into an extension, not a creation.

**Option C — Defer all inferlet/job coverage to P3 and delete P1.5.**
Fold P1.5's acceptance into P3.2 ("Every code-bearing tool call is captured" — inferlets/jobs are code-bearing). Simplest, but loses the explicit M-sized inferlet/job line item and its 4 unit + 2 E2E tests.

**Scout recommendation: Option A.** It honors REGRA #0 (potentialize — P1.5 stays a full deliverable), keeps the test budget, and removes the contradiction by a pure re-sequencing edit (`deps: P1.1` to `deps: P3.2`, move under §P3). Option B is the fallback if the planner wants P1 to remain a complete vertical slice; in that case P3.2's "New symbols" line **must** be edited to say "extends `ExecSurface`" so two waves don't both claim to *create* the enum.

**Either way the plan must be edited** — P3.2 and P1.5 currently both list `ExecSurface*` under "New symbols", which is the canonical double-creation anti-pattern.

## 2. inferlets execution path

### 2.1 CLI to daemon to WASM

```
touring inferlets run <name> [<input>]
  -> cli/inferlets.rs:27-45  run()  ->  daemon_query("cli-inferlets-run", {name, input})
        -> hook_registry.rs:1396-1398  "cli-inferlets-run" -> cli_handlers::cli_inferlets_exec
              -> cli_handlers.rs:4261-4316  cli_inferlets_exec(rt, payload)
                    - maps name -> InferletKind {AlwaysSuccess|Memory|Pattern|Classifier}
                    - rt.ctx.inferlet_service  (Option<InferletService>)
                    - spawns "inferlets-eval" thread -> Runtime::new().block_on(
                           service.evaluate_async(kind, input))
                             -> inferlets.rs:200  InferletService::evaluate_async
                                   -> inferlets.rs:184  InferletService::evaluate
                                         -> inferlets.rs:79  (trait) evaluate -> AsyncInferletPool
                                               -> touring_wasm::WasmRunner  (WASM sandbox)
```

**Key facts (verified):**
- CLI dispatcher: `crates/touring-server/src/cli/inferlets.rs:20` `pub fn run(args)`. The `run` subcommand at `:27-45` builds `{name, input}` and calls `daemon_query("cli-inferlets-run", payload)`.
- **Plan naming caveat**: the registry key is `cli-inferlets-run` but the handler fn is **`cli_inferlets_exec`** (`hook_registry.rs:1397`, `cli_handlers.rs:4261`) — NOT `cli_inferlets_run`. There is no `cli_inferlets_run` symbol. A wave grepping for `cli_inferlets_run` will find nothing.
- WASM runner: inferlet bodies are real WASM modules (`crates/inferlets/` has the source `.rs`/`.js`/`.py`; `inferlets_assets.rs` embeds compiled `.wasm`). Execution is `AsyncInferletPool` -> `touring_wasm::WasmRunner` (`inferlets.rs:35`).
- The 4 valid kinds are a **fixed enum** `InferletKind` (`AlwaysSuccess|Memory|Pattern|Classifier`), `inferlets.rs`. Inferlets are **not arbitrary user code at run-time** — they are pre-compiled, pre-registered WASM. This matters for CEG: the threat surface is "is this WASM blob trusted?", not "scan inline source".

### 2.2 Where a pre-execution validation hook attaches (P1.5)

**Primary insertion point: `cli_handlers.rs:4261` `cli_inferlets_exec`, immediately after `kind` is resolved (after line 4283) and before the eval thread is spawned (before line 4298).**

This is the single chokepoint — both the CLI path and any MCP path land here. A `route_through_gateway()` / `validate_exec_surface(ExecSurface::Inferlet, ...)` call inserted at line ~4284 gates 100% of inferlet executions. The handler already returns structured JSON `{status, error}` so a "blocked" verdict fits the existing return shape with zero signature change.

Secondary (defense in depth, optional): `inferlets.rs:200 evaluate_async` — but this is reached by other internal callers (blast_radius 28, see §6) so gating there risks blocking trusted internal use. **Gate at the handler, not at `evaluate_async`.**

## 3. jobs execution path

### 3.1 CLI to daemon to execve

```
touring jobs spawn <program> [args...]
  -> cli/jobs.rs:26-49  run()  ->  daemon_query("cli-jobs-spawn", {tool_name, program, args})
        -> hook_registry.rs:1365-1366  "cli-jobs-spawn" -> cli_handlers::cli_jobs_spawn
              -> cli_handlers.rs:4324-4347  cli_jobs_spawn(rt, payload)
                    - extracts {tool_name, program, args}
                    - guard: program non-empty; tokio runtime present
                    - shared::job_registry::spawn_worker(tool_name, program, &args)
                          -> shared/job_registry.rs:179  spawn_worker -> execve, no shell
                                -> DashMap<String, JobState>  (global JobRegistry singleton)
```

**Key facts (verified):**
- CLI dispatcher: `crates/touring-server/src/cli/jobs.rs:26` `pub fn run(args)`. `spawn` at `:30-49`.
- Daemon handler: `crates/touring-hooks/src/cli_handlers.rs:4324` `pub fn cli_jobs_spawn(_rt, payload)` — note `_rt` is **unused** today.
- Worker spawn: `crates/touring-hooks/src/shared/job_registry.rs:179` `pub fn spawn_worker(tool_name, program, args) -> String` (returns `job_id`). Uses `execve` semantics — **no shell interpolation** (documented `cli/jobs.rs:17-20`; injection-safe).
- Global registry: `job_registry.rs:116` — a process-global singleton `DashMap<String, JobState>`.
- The job runs an **arbitrary external program** the user names (`touring jobs spawn cargo test`, but equally `touring jobs spawn python3 /tmp/x.py`). This IS an open code-execution surface — exactly what CEG must gate. Unlike inferlets (fixed WASM set), jobs run any binary on `$PATH`.

### 3.2 Where validation attaches (P1.5)

**Primary insertion point: `cli_handlers.rs:4324` `cli_jobs_spawn`, after the `program.is_empty()` guard (after line 4336) and before `spawn_worker` is called (before line 4341).**

A `validate_exec_surface(ExecSurface::Job, program, &args)` call here gates every `jobs spawn`. The handler returns `{error}` JSON on the empty-program path already, so a blocked-verdict JSON is a natural fit. **Bonus**: `_rt` (currently unused) gives the handler access to `HookRuntime` — the gateway can pull project capability profile / RL state from `rt` with no signature change.

Secondary: `job_registry.rs:179 spawn_worker` has blast_radius 15 and is called from `tools_infra.rs`, `decomposer.rs`, `cortex/runtime.rs` etc. — gating there would block trusted internal spawns. **Gate at `cli_jobs_spawn`, not at `spawn_worker`.**

## 4. `extract_file_context` (P1.6 reused symbol)

**Found — but it is a homonym with 2 definitions.** VP-Scout Cadeia 4 (homonimia):

```
$ touring index find extract_file_context -j
{"count":2,"definitions":[
  {"file_path":"crates/touring-hooks/src/pre_bash.rs","line":276},
  {"file_path":"crates/touring-hooks/src/post_bash.rs","line":563}]}
```

| Definition | Signature | What it extracts |
|---|---|---|
| `pre_bash.rs:276` | `pub fn extract_file_context(command: &str) -> Option<String>` | First file path matched by `FILE_PATH_RE` (regex, imported `pre_bash.rs:19` from `shared::patterns`) in a bash **command string**. Returns the path or `None`. |
| `post_bash.rs:563` | (separate definition — not read in full) | post-execution variant |

**For P1.6 the relevant one is `pre_bash.rs:276`** — it parses a path out of a command *before* execution, which is exactly what temporal-split detection needs ("a script written then run later" -> the second turn's command names the staged file path). The function is a thin regex wrapper: `FILE_PATH_RE.captures(command).get(1)`.

**Caveat for the implementation wave**: it returns only the **first** path and only matches the `FILE_PATH_RE` shape (in `shared/patterns.rs`). It does NOT distinguish "a file being created" from "a file being executed". P1.6 will likely need either a richer extractor or to pair `extract_file_context` with surface classification. Recommend the wave verify `FILE_PATH_RE`'s exact pattern in `shared/patterns.rs` before assuming coverage of e.g. `bash /tmp/foo.sh` vs `python3 ./build.py`.

## 5. `sandbox_executor.rs` structure + StagingRegistry attach point (P1.6)

### 5.1 Structure (`crates/touring-hooks/src/sandbox_executor.rs`, 881 lines, 48 symbols)

Module purpose (header `:1-15`): **D2.2 SandboxExecutor** — isolated subprocess execution for context-mode routing. Runs large-output commands in a subprocess, captures stdout to disk, returns a blake3 `content_hash`.

| `resolve_language_runtime` / `resolve_language_args` | 120 / 162 | language -> runtime binary + argv |
| `resolve_args` | 184 | tool_name + JSON args -> argv. **Handles `Bash` with `script` field and `Sandbox*` tools** |

| **`tee_dir` / `store_tee` / `read_tee` / `cleanup_tee`** | 581 / 601 / 619 / 628 | NEW-2 failure-tee subsystem |

### 5.2 How heredoc / multi-line scripts are handled today

**They are NOT, as a temporal concept.** Verified:
- `resolve_args` (`:184-240`) handles a multi-line script only as an **inline string in the same call**: `Bash` -> `["-c", cmd]` (`:191`); `Sandbox*`/`Bash`-with-`script` -> `resolve_language_args(lang, script)` (`:236`). A heredoc is just bytes inside that `command`/`script` string at execution time.
- There is **no notion of "a script written in turn N, executed in turn N+M"**. Each `execute_in_sandbox` call is fully stateless w.r.t. prior turns.
- The only persistent on-disk state is: (a) `store_output` -> `sandbox_outputs/<hash>.bin` (captured *output*, not input); (b) `store_tee` -> `tee/<hash>.log` (failure *output*). **Neither records the code body, its origin turn, nor a verdict.**
- `tee_dir()` (`:581`) resolves `~/.claude/touring/tee` or `$TOURING_TEE_DIR`. `cleanup_tee(retention_secs)` (`:628`) GCs by mtime. This is the closest existing pattern to what `StagingRegistry` needs (a hashed, on-disk, GC'd store) — but it stores outputs, not staged source.

**Conclusion**: the temporal-split gap the plan names (R9, `plan:529`) is real and unmitigated today. A script can be written via `Write` to `/tmp/x.sh` in one turn and executed via `bash /tmp/x.sh` in a later turn; nothing in `sandbox_executor.rs` connects those two events.

### 5.3 Where the `StagingRegistry` stub attaches (P1.6)

`sandbox_executor.rs` has blast_radius **4** (consumers: `cli_handlers_mcp.rs`, `tool_output_router.rs`, 2 test files) — **low risk**, safe to extend.

**Recommended P1.6 stub design — a new sibling module + 1 call site:**

1. **New module `crates/touring-hooks/src/staging_registry.rs`** (or `sandbox/staging.rs`). Stub surface:
   - `pub struct StagingRegistry` — wraps a `DashMap<PathBuf, StagedEntry>` (mirror the `JobRegistry` global-singleton pattern at `job_registry.rs:116`, and the `tee_dir` on-disk pattern at `sandbox_executor.rs:581`).
   - `pub struct StagedEntry { origin_turn, written_at, content_hash, verdict: Option<...> }`.
   - Stub methods: `register(path, hash)`, `lookup(path) -> Option<StagedEntry>`, `record_verdict(path, verdict)`. For P1.6 (stub) these can be in-memory only; P5.2 ("staging registry — full", `plan:388-393`) makes it persistent + verdict-aware.

2. **Call site A — record on write**: where `Write`/`Edit` of a code-bearing file is observed. The post-write hook path is `post_write` / `post_edit`; recording a staged file when a `.sh`/`.py` is written is the "write-side" of the temporal pair. (P1.2 already adds `.sh` to Write/Edit matchers — `plan:132` — so the hook fires.)

3. **Call site B — check on execute**: inside `resolve_args` (`sandbox_executor.rs:184`) or just before `cmd.spawn()` in `execute_in_sandbox` (`:265-267`). After extracting the target path (via `extract_file_context`, §4), call `StagingRegistry::lookup(path)`. If the path is a previously-staged file with no verdict -> force full re-analysis (the R9 mitigation, `plan:529`).

**Cleanest single anchor for the stub**: add the `lookup` check at `execute_in_sandbox` line ~253 (right after `resolve_args`, before `Command::new`). That is the universal execution chokepoint for the sandbox path — every `Sandbox*` and `Bash`-with-`script` execution flows through it.

> Note: `execute_in_sandbox` is the sandbox/context-mode path. A plain `Bash: bash /tmp/x.sh` that is NOT routed to sandbox flows through the `pre-bash` hook instead — P1.6's `extract_file_context` is in `pre_bash.rs`, so the **pre-bash hook is the other natural StagingRegistry check site**. The wave should wire `StagingRegistry::lookup` into BOTH (`pre_bash.rs` for un-sandboxed bash, `execute_in_sandbox` for sandboxed) for full temporal-split coverage. The plan's "Files: sandbox_executor.rs; staging registry stub" under-specifies this — recommend the wave also touch `pre_bash.rs`.
