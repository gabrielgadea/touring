# CEG — P4.3 rlimit / cgroup resource caps (wave report)

> Pln2 plan: `docs/2026-05-17-ceg-pln2-plan.md`, deliverable **P4.3**.
> Executed 2026-05-18. FASE 0 gate PASS (`cargo check --workspace` exit 0).
> **Phase P4 — 3 of 6 deliverables.** Per-execution resource capping becomes
> universal: the X5 sandbox path is now resource-capped, not only X8.

## 1. What P4.3 adds

Before P4.3, only the X8 SUPERVISED-EXEC stage (`run_supervised`, P4.2) capped
its child's resources. The X5 dry-run path — `execute_in_sandbox` and the
compiled-language runners — ran **uncapped**: a runaway dry-run could burn
unbounded CPU or open unbounded file descriptors. P4.3 closes that with a
unified per-execution bundle, [`ResourceLimits`], and a single wiring point,
[`apply_resource_caps_to`], that every sandboxed `Command` routes through.

It also adds an honest probe — [`cgroup_v2_status`] — for the stronger,
group-level capping layer (`memory.max`, `pids.max`), reporting precisely when
that layer is and is not available rather than pretending it is always on.

## 2. The plan said "new symbol" — VP-Scout corrected it (FIX-S4)

The Pln2 plan listed P4.3 as introducing `ResourceCaps` and `apply_rlimit`. A
VP-Scout Cadeia 3 (already-implemented) check showed both **already shipped** in
`capability/enforce_linux.rs` — delivered early as part of P2.4-A. The plan was
**STALE** on that point: plan docs describe INTENT, not the current code state.

The *real* gap was not the cap primitive — it was that the X5 path never
**applied** it. P4.3 was re-scoped to the wiring: a new `capability/limits.rs`
that bundles the existing caps into a per-execution `ResourceLimits` and wires
it into the sandbox `Command` builders.

## 3. What shipped

### `capability/limits.rs` (new)

| Symbol | Purpose |
|--------|---------|
| `ResourceLimits` | The per-execution bundle — wraps the `rlimit` `ResourceCaps` |
| `ResourceLimits::sandboxed` | Conservative caps for an untrusted run — CPU 30s, 256 FDs, 256 MiB file size |
| `apply_resource_caps_to` | Wires the caps into a sandbox `Command` via a child pre-exec closure (Linux); no-op on other targets |
| `CgroupStatus` | `Available { own_dir }` / `Unavailable { reason }` — never a silent gap |
| `cgroup_v2_status` | Honest host probe for group-level (`memory.max` / `pids.max`) capping |

`apply_resource_caps_to` was wired into **four** sandbox call sites in
`sandbox_executor.rs`: `execute_in_sandbox` (the X5 dry-run), `compile_and_run_go`,
and both the compile and the run steps of `compile_and_run_rust`.

## 4. The regression — `RLIMIT_AS` and `RLIMIT_NPROC` are the wrong caps

The first cut applied `ResourceCaps::sandboxed_defaults()` — which caps
`RLIMIT_AS` (512 MiB) and `RLIMIT_NPROC` (64) — to the compiled-language path.
It **broke every P4.1 test**. Two root causes, both worth recording:

- **`RLIMIT_AS` caps *virtual* memory, not RSS.** Compiler toolchains and
  numeric runtimes routinely `mmap` gigabytes of address space while touching
  little physical RAM. A 512 MiB `AS` cap aborts `rustc` / `go` outright.
- **`RLIMIT_NPROC` is enforced per *real UID*, not per execution.** On a shared
  desktop account the UID already runs hundreds of processes — so *any* low
  `NPROC` cap makes every `fork` the child attempts fail with `EAGAIN` (e.g.
  `rustc` forking its linker). It is a system-wide-per-user limit wearing the
  costume of a per-process one.

**Fix.** [`ResourceLimits::sandboxed`] caps only the rlimit classes that
`setrlimit` bounds *cleanly per process*: `RLIMIT_CPU` (30 s), `RLIMIT_NOFILE`
(256), `RLIMIT_FSIZE` (256 MiB). `address_space_bytes` and `processes` are left
`None` — and the doc-comment says exactly why, pointing at cgroup as the right
home for per-execution memory and process-count limits.

## 5. cgroup v2 — probed honestly, not faked

Per-execution *memory* and *process-count* capping genuinely belongs to cgroup
v2's `memory.max` / `pids.max` — those are per-cgroup, immune to the `RLIMIT_AS`
/ `RLIMIT_NPROC` flaws above. But an unprivileged process can only create a
capping cgroup inside a **delegated** slice: cgroup v2's no-internal-processes
rule otherwise blocks controller delegation.

`cgroup_v2_status` reports that precondition truthfully. It returns
`Available { own_dir }` only when cgroup v2 is mounted, the process's own cgroup
directory is resolvable, and `cgroup.controllers` exposes both `memory` and
`pids`; otherwise `Unavailable { reason }` names the exact obstacle. The rlimit
baseline holds unconditionally — this probe governs only the optional stronger
layer. No silent gap, no false checkbox: a host without a delegated slice is
*told so*, and still gets the CPU / FD / file-size caps.
