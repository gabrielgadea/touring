**Location**: `crates/touring-server/src/tools/ctx_execute_tools.rs:71-104`

### Behaviour today

| Property | Reality |
|---|---|
| **Matching technique** | **Substring** — `code.contains(pattern)` at line 99. NOT AST-based. |
| **Language coverage** | **3 of 11** — `JavaScript`/`TypeScript` (shared arm, 7 patterns), `Python` (7 patterns), `Shell` (2 patterns). The `match` has `_ => &[]` (line 96) for **Ruby, Go, Rust, Php, Perl, R, Elixir** — zero patterns, always returns empty. |

### Substring-match weaknesses (why P1.3 wants AST)

- Bare-token matching hits inside string literals and comments — false positives.
- Spacing/aliasing variations slip past — false negatives.
- The doc comment in `ast_grep_signal.rs:12-14` explicitly contrasts: "ast-grep's structural matcher distinguishes string-literal occurrences and comments from real call sites." Regression test `scan_source_excludes_unwrap_in_string_literal` (`ast_grep_signal.rs:452`) proves the AST path already handles this correctly.

## 7. ast-grep best-practice notes (context7)

`ast-grep-core 0.36.0` (workspace-pinned, `Cargo.toml:399`). Pattern syntax (confirmed via context7 `/ast-grep/ast-grep`):
- `$VAR` = one node; `$$$ARGS` = zero-or-more nodes; `$_` = wildcard no-capture.
- Forbidden-call patterns for P1.3 are simple call-shapes — the dangerous function name followed by `($$$)`. These are exactly the `PatternEntry.pattern` form already used in `risk_patterns.rs` (e.g. the existing Python dynamic-exec entry at `risk_patterns.rs:54-57`).
- **Production gotcha already handled**: `search()` (`touring-code/src/polyglot/search.rs:38-43, 100-112`) rejects bare-ellipsis patterns (`$$$` alone) — they would `debug_assert!`-panic inside `ast-grep-core 0.36.0`'s `match_tree/mod.rs:82`. P1.3 patterns must always anchor the ellipsis inside a call shape, never bare. `Pattern::try_new` is used (fallible) — malformed patterns return `Err`, not panic.
- **Fallback when grammar is absent** (Perl/R): ast-grep gives no path. The recommended fallback is the **existing substring approach retained for those 2 languages** — i.e. keep the current `code.contains(pattern)` arms for `Perl` and `R`. ast-grep docs offer `regex:` as a rule operator but that still requires a parsed tree; with no grammar, plain substring/text-regex on raw source is the only option.

## 8. RECOMMENDATION for P1.3 — **OPTION (b): HYBRID**

**Adopt the hybrid model. Do NOT attempt AST for all 11 — it is impossible: ast-grep has no Perl and no R grammar, and adding tree-sitter-perl/tree-sitter-r as new workspace deps would not help because `ast-grep-language 0.36.0`'s `SupportLang` enum is closed (no `Perl`/`R` variant — you cannot register a grammar ast-grep does not know).** The hybrid is: **AST-based (`scan_source` + new forbidden `PatternSet`s) for the 9 languages with grammars — JavaScript, TypeScript, Python, Ruby, Go, Rust, Php, Elixir, Shell(Bash)** — and a **documented substring fallback retained for the 2 grammarless languages, Perl and R**. Concretely: (1) add `Lang::Elixir` to `touring-code/src/polyglot/lang.rs` (4 small arms); (2) create security-grade forbidden `PatternSet` consts (a new `forbidden_patterns` set, separate from the pre-read `risk_patterns.rs` defensive sets); (3) add a `SandboxLanguage` to `polyglot::Lang` mapper; (4) implement the plan's new symbol `ast_forbidden_scan` calling `touring_hooks::shared::ast_grep_signal::scan_source`; (5) in `detect_forbidden_calls`, dispatch: grammar-backed langs to `ast_forbidden_scan`, `Perl`/`R` to the substring arms (today they are empty `_ => &[]` — populate them with curated substrings + a code comment marking them as the documented fallback). The 9-of-11 AST coverage with `partial`/fail-open semantics already battle-tested in `scan_source` satisfies acceptance criterion "uses ast-grep, not naive substring match" for every language where it is technically possible, and the R3 risk row's false-positive concern is resolved for those 9. The `ast-grep-core 0.36 to 0.42` upgrade noted in the plan (line 549) is **optional for P1.3** — 0.36.0 already has all 9 needed grammars; defer the upgrade unless the W11.6 fuzz follow-up drives it independently.
