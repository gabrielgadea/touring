## 1. What P3.6 adds

P3.6 closes the *judgement* half of the gateway. X5 ran the code once in the
sandbox; X6 and X7 turn the accumulated evidence into a verdict:

- **X6 CAPABILITY-GATE** (`gateway/gate.rs`) — asks *if this code runs for
  real, what authority would it exercise, and does the granted profile permit
  it?* It derives the required [`Capability`] set and resolves each against the
  granted `CapabilityProfile`.
- **X7 DECISION** (`gateway/decision.rs`) — fuses all five pipeline signals
  (X2..X6) into one composite score and one `Allow` / `Warn` / `Deny` verdict.

`Decided` (X7's output) is the typestate's terminal state — there is no
transition onward, so the `GateDecision` is the pipeline's final word.

## 3. What shipped

### X6 — `gateway/gate.rs`

| Symbol | Purpose |
|--------|---------|
| `required_capabilities` | Lexically derives the `Capability` set a code body would exercise |
| `CapabilityNeed` | A required capability + the operation token that revealed it |
| `gate_capabilities` | Resolves each need against a `CapabilityProfile` |
| `GateReport` / `GatedCapability` | The X6 result; `worst_decision` / `is_clear` / `first_blocking_denial` / `has_blocking_denial` / `denied` |
| `capability_class` | Stable label for an authority class (`subprocess`, `file-write`, …) |
| `Execution::<SandboxTested>::capability_gate` | The X5→X6 transition to `Gated` |

`required_capabilities` is a **lexical, fail-closed heuristic** — the same
discipline as X3's `extract_symbols`. A bash surface is tokenised into shell
commands (separator split, directory-prefix stripped so `/bin/rm` → `rm`,
`VAR=val` prefixes skipped, `>`/`>>`/`tee` redirections detected, `2>&1` fd
duplication excluded); a code surface is scanned against per-class token
tables. When a scope cannot be determined it is recorded at its broadest
(`FsWrite` of `/`, `Run` of an unknown command), so it resolves against the
profile's *default* — under a deny-by-default profile that fails **closed**.
`FsRead` is deliberately not detected: every built-in profile already grants
workspace read, so flagging it would be pure noise.

### X7 — `gateway/decision.rs`

| Symbol | Purpose |
|--------|---------|
| `composite_score` | Fuses the five evidence signals into one score in `0.0..=1.0` |
| `Verdict` | `Allow` / `Warn` / `Deny` |
| `GateDecision` | Verdict + composite score + human reasons + canonical fix |
| `GateDecision::from_evidence` | The X7 logic |
| `Execution::<Gated>::decide` | The X6→X7 transition to terminal `Decided` |

`composite_score` is a flat weighted mean of five `*_subscore` helpers — X2
STATIC and X6 CAPABILITY-GATE carry `0.25` each (half the weight between the
two hard security gates), X5 SANDBOX `0.20`, X3 VGP and X4 PREDICT `0.15` each.
Each helper is a pure `fn(Option<&Report>) -> f64`, individually testable; a
not-yet-run stage scores a neutral value, so the score is defined for a
partially-advanced execution.

**Deny-wins.** A high composite score never overrides a hard block:
`StaticSeverity::Block`, or a denied *high-authority* capability
(subprocess / file-write / network), forces `Verdict::Deny` regardless of the
other signals — the same deny-wins discipline the capability model itself
uses. A denied `Env` capability is a `Warn`, not a hard block: a generic
environment read cannot be told from a credential read at the lexical level.
The verdict ladder: hard block or composite `< 0.5` → `Deny`; composite
`>= 0.85` with no reason on the ledger → `Allow`; otherwise → `Warn`. Every
non-`Allow` verdict carries a single canonical, actionable fix.

### Typestate extension — `gateway/typestate.rs`

`Evidence` gained `gate_report` and `decision` (`Option<…>`). Each transition
is the sole writer of its field; the `..Evidence::default()` seed needs no
constructor change.

## 5. Notes — three gotchas worked around

1. **Plugin security hook.** The `security-guidance` plugin's PreToolUse hook
   blocks any `Write` whose content contains certain risk-pattern literals
   (subprocess- and deserialization-related call forms). The X6 token catalogue
   is a *detector* of those patterns, not a user — a false positive. The one
   offending literal was dropped from the run-detection table; the bare
   `system(` token already covers every real call site of it, so detection is
   unaffected.
2. **`predict` arity.** X4's `predict` takes `&ExecutionOutcomePredictor` plus
   the history closure — two arguments.
3. **f64 JSON roundtrip.** `serde_json`'s default float parser is not
   correctly-rounded (it lacks the `float_roundtrip` feature), so a
   `composite_score` `f64` can shift by ~1 ULP across a JSON roundtrip. The
   serde test compares the discrete fields exactly and the float within a
   `1e-9` tolerance — far below any score difference that could change a
   verdict.
