# CEG — P4.4 bounded subprocess pool + backpressure (wave report)

> Pln2 plan: `docs/2026-05-17-ceg-pln2-plan.md`, deliverable **P4.4**.
> Executed 2026-05-18. FASE 0 gate PASS (`cargo check --workspace` exit 0).
> **Phase P4 — 4 of 6 deliverables.** The gateway now bounds *itself*: a burst
> of code-bearing tool calls can no longer spawn subprocesses without limit.

## 1. What P4.4 adds

The gateway exists to stop untrusted code exhausting the host. P4.4 closes the
last way it could exhaust the host *itself*: every X5 dry-run and every X8
SUPERVISED-EXEC spawns an OS subprocess, and nothing capped how many ran at
once (CEG Pln2 risk R5). [`ExecPool`] is that cap — a `tokio` [`Semaphore`]
holding `N` permits. A caller takes a permit before spawning and holds it until
the subprocess exits, so the daemon never has more than `N` sandboxed
subprocesses live at once.

**Backpressure, not failure.** When all `N` slots are busy, `acquire` does not
fail — it **queues**, waiting up to `acquire_timeout` for a slot, and returns
`PoolError::QueueTimeout` only if that whole window elapses. Excess load is
*shaped*, never silently dropped and never unbounded.

## 2. The plan said "new symbol ExecPool" — VP-Scout confirmed it

`touring index find ExecPool` returned 3 hits — but `grep -rn ExecPool crates/`
(VP-Scout Cadeia 7, anti-staleness) returned **zero**: the index hits were
stale/fuzzy artifacts, `ExecPool` is genuinely new. The plan's `JobRegistry
pattern` reuse note is honoured as *style* guidance (atomic-counter
observability, snapshot stats) — `ExecPool` is a distinct concept (a
concurrency limiter, not a job registry), so nothing is imported from it.

## 3. The single chokepoint — one edit covers X5 *and* X8

Discovery found that **every** async subprocess spawn routes through one
function — `sandbox_executor::spawn_and_capture`:

| Caller | Stage | Routes via |
|--------|-------|------------|
| `execute_in_sandbox` | X5 | `spawn_and_capture` |
| `compile_and_run_go` | X5 | `spawn_and_capture` |
| `compile_and_run_rust` | X5 | `spawn_and_capture` ×2 (compile + run, sequential) |
| `run_supervised` | X8 | `spawn_and_capture` |

So gating `spawn_and_capture` **once** bounds the entire X5+X8 surface. No
nested acquisition exists: `compile_and_run_rust`'s two calls are *sequential*
— each acquires and releases cleanly, never holding two permits, so the pool
cannot deadlock on itself.

## 4. What shipped

### `gateway/exec_pool.rs` (new)

| Symbol | Purpose |
|--------|---------|
| `ExecPool` | The bounded pool — a `tokio::Semaphore` of `N` permits + lifetime counters |
| `ExecPool::global` | The process-global pool (`OnceLock`) — makes "never more than `N`" a daemon-wide guarantee |
| `ExecPool::acquire` | Take a slot, **queueing** under backpressure up to `acquire_timeout` |
| `ExecPool::try_acquire` | Take a slot **without waiting** — `PoolError::Saturated` at once if full |
| `ExecPool::{available, in_flight, stats}` | Live observability |
| `PoolConfig` | Sizing + timeout; `from_env` (env override) over a pure, testable `resolve` core |
| `PoolError` | `QueueTimeout` / `Saturated` — closed enum, `kind()` label, `Display`, `Error` |
| `PoolStats` | A snapshot: cap, in-flight, available, total acquired / timed-out / rejected |

### `sandbox_executor.rs` — the wiring (1 edit)

`spawn_and_capture` now opens with:

```rust
let _pool_slot = ExecPool::global()
    .acquire()
    .await
    .map_err(|e| SandboxError::Spawn(format!("{e}")))?;
```

The `_pool_slot` permit is held for the whole spawn+capture and released on
every return path — success, timeout, or error. A pool timeout folds into
`SandboxError::Spawn` (zero blast on the `SandboxError` enum); the gateway's
own `GatewayError` stays the closed, entry-layer-only enum P3.7 designed.

### `gateway/mod.rs`

`pub mod exec_pool;` + `pub use exec_pool::{ExecPool, PoolConfig, PoolError,
PoolStats};` + a `P4.4` row in the phase-layout table.

## 5. Design notes

- **`OwnedSemaphorePermit`, not a newtype.** `acquire` / `try_acquire` return
  tokio's permit directly — the tokio-documented idiom (Context7:
  `let _permit = semaphore.acquire_owned().await`). The pool is the new
  abstraction; the permit is tokio's RAII guard, used as tokio intends.
- **`PoolConfig::resolve` is a pure core.** `from_env` reads the two env vars
  (`TOURING_CEG_MAX_CONCURRENT`, `TOURING_CEG_ACQUIRE_TIMEOUT_SECS`) and
  delegates to `resolve(Option<String>, Option<String>)` — so the resolution
  logic (clamp, garbage/zero fallback) is unit-tested without mutating
  process-global env state.
- **Cap derivation.** The default `max_concurrent` is the host CPU count,
  clamped to `[1, 256]`; a mistyped env var cannot ask for thousands of
  subprocesses, and a zero cannot deadlock the pool.
- **Loud on saturation.** An `acquire` timeout emits `tracing::warn!` — a
  saturated pool is a real degradation the operator should see, not a silent
  backpressure event.

13 tests added (plan asked 7 + 2). The two E2E prove both halves of the
acceptance:

- `p44_concurrent_sandbox_runs_route_through_the_exec_pool` — runs a batch of
  real sandbox executions concurrently and asserts the global pool's
  `total_acquired` moved by at least the batch size: the pool **is** in the
  X5 path, not bypassed.
- `p44_exec_pool_caps_live_subprocesses_at_the_configured_max` — drives 8 tasks
  through a cap-2 pool, each holding its permit across a real subprocess, while
  a sampler watches `in_flight`: it never exceeds 2, and all 8 complete (the
  excess queued, none dropped). That **is** the "never more than `N`
  subprocesses" guarantee, observed.
