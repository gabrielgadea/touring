## 1. What P4.5 adds

X5 SANDBOX runs the code body once in a real subprocess — and that run is
dominated by interpreter cold-start (`python3` / `node`: tens to hundreds of
milliseconds). When the *same* code body is gated again — a retried tool call,
a re-run of an identical snippet — that cost is pure waste.

[`DryRunCache`] removes it: a `moka` cache keyed by a **BLAKE3 digest** of the
`(tool, payload, capability profile)` triple. The first dry-run of a body runs
the sandbox and stores its [`SandboxOutcome`]; every later dry-run of a
byte-identical body returns the stored outcome and **skips the subprocess
entirely**.

The `ceg_baseline.rs` bench (P0.4) already anticipated this: its header notes
that interpreter cost "is tracked separately via the X5 dry-run cache hit-rate
(P4.5)". P4.5 is that cache.

## 4. Design notes

- **Why the profile is in the key.** The capability profile sets the sandbox
  timeout (`Deny` → 5 s, `Allow` → 30 s). The *same* body can time out under a
  short leash yet finish under a long one — so their outcomes must not share a
  cache slot. The key hashes `tool \0 payload \0 profile_name`; the `\0`
  separators stop `("ab","c")` colliding with `("a","bc")`.
- **All outcomes cached, including failures.** A timeout or a spawn failure for
  an identical body is deterministic enough to reuse — and caching a timeout
  *saves* the 5–30 s re-wait. The 1-hour TTL bounds any staleness.
- **`CacheConfig::resolve` is a pure core.** `from_env` reads
  `TOURING_CEG_DRY_RUN_CACHE_CAPACITY` / `…_TTL_SECS` and delegates to
  `resolve(Option<String>, Option<String>)` — so the clamp / garbage-fallback
  logic is unit-tested without mutating process-global env state (the same
  pattern as P4.4's `PoolConfig`).
- **Accurate `entry_count`.** `stats()` calls `moka`'s `run_pending_tasks()`
  before `entry_count()` so the reported entry count is exact, not lagging.

9 unit tests added (plan asked 6) + 1 criterion bench. The acceptance is
hard-gated by two of them:

- `cached_dry_run_skips_the_sandbox_on_a_repeat_body` — runs a real bash
  dry-run once, then a second time on the byte-identical body; the global
  cache's `hits` counter moves on the repeat and `misses` on the first — the
  cache **is** in the X5 path, and the repeat skipped the subprocess.
- `p45_cache_hit_latency_p99_under_5ms` — measures 2 000 warm cache-hit
  lookups (the full `dry_run_cache_key` + `moka` get path) and asserts the P99
  is under 5 ms. It is sub-microsecond in practice — orders below the budget.
