## 1. What P3.5 adds

X5 SANDBOX (`gateway/sandbox_stage.rs`) runs the code body **once, in the
sandbox** — a real subprocess under a wall-clock timeout — before any
unsandboxed run is permitted. The X6/X7 gate then decides on *evidence of
behaviour*, not just static inspection. This is the first stage that actually
executes the code (in isolation).

## 2. VGP — the two reused symbols, plan corrections

| Symbol | Verdict |
|--------|---------|
| `execute_in_sandbox` | The verified in-repo symbol is **`execute_in_sandbox_blocking`** (`sandbox_executor.rs:359`) — the synchronous wrapper, correct for a blocking transition. |
| `SandboxConfig` | ✅ `sandbox_executor.rs:28` — `timeout_ms` / `max_output_bytes` / `fallback_on_timeout`. |

`SandboxResult` (the executor's return) captures `exit_code`, `output_bytes`,
`was_truncated`, `content_hash` (BLAKE3 of stdout) and `stored_path` — not
stdout/stderr inline. X5's `SandboxOutcome` records exactly what the executor
provides.

## 3. What shipped — `gateway/sandbox_stage.rs`

| Symbol | Purpose |
|--------|---------|
| `SandboxOutcome` | The dry-run result — exit code, output size, truncation, timeout, content hash, gating profile name; `succeeded()` |
| `SandboxCapabilities` | The dry-run parameters derived from a `CapabilityProfile` |
| `dry_run_in_sandbox` | The production runner — reuses `execute_in_sandbox_blocking` |
| `Execution::<Predicted>::sandbox_dry_run` | The X4→X5 transition to `SandboxTested` |

`SandboxCapabilities::from_profile` reads the profile's
`default_decision()`: a `Deny`-default (restrictive) profile gets a 5 s leash,
`Prompt` 15 s, `Allow` the full 30 s. `dry_run_in_sandbox` folds a timeout or a
spawn failure into the `SandboxOutcome` rather than propagating, so X5 always
yields an outcome for the gate to weigh. `sandbox_dry_run` is closure-driven —
unit tests pass a mock (no subprocess), while the production wiring (P3.7)
passes `dry_run_in_sandbox`.

## 4. Capability scope — honest boundary

P3.5 delivers the X5 *stage*: the dry-run runs under a capability-derived
`SandboxConfig` and records which profile gated it. The deeper **kernel-level
enforcement** — feeding the profile's resource caps into the subprocess via
`apply_rlimit` (P2.4-A) / landlock (P2.4-B) — is **P4 (Sandbox Completion &
Hardening)**. This is consistent with the P2.4 split that already shipped
`apply_rlimit` and deferred the landlock body. P3.5 does not edit
`sandbox_executor.rs`: threading a capability field through that file's
execution path is the P4 hardening concern, and P2.4-B (landlock) is itself a
pending online sub-wave. The X5 *stage* is complete; the executor-internal
enforcement is the P4 wiring.
