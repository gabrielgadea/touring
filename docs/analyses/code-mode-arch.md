Arquitetura de Agentes Baseada em "Code Mode": Design de Código, Aderência de LLMs e Blueprint de Infraestrutura1. Sumário Executivo e Matriz de Ruptura de ParadigmaA orquestração de Modelos de Linguagem de Grande Porte (LLMs) em sistemas agênticos passa por uma transição estrutural. O paradigma histórico — fundamentado em chamadas atômicas e serializadas via JSON-RPC, tais como o OpenAI Function Calling, o Anthropic Tool Use tradicional e o Model Context Protocol (MCP) em sua implementação estritamente declarativa — apresenta gargalos severos de escalabilidade. Em cenários industriais complexos, exigir que o modelo execute individualmente cada ferramenta gera uma degradação expressiva da janela de contexto e multiplica a latência devido a sucessivas viagens de ida e volta (round-trips) entre o cliente e o provedor de inferência.A emergência do paradigma Code Mode — conceitualizado por Kenton Varda e Sunil Pai na Cloudflare e operacionalizado por ecossistemas como o TanStack AI Code Mode e o DeepSeek Harness — redefine essa dinâmica. Em vez de expor centenas de assinaturas JSON ao contexto e aguardar execuções atômicas encadeadas, o Code Mode disponibiliza ao agente um ambiente de execução isolado (sandbox) e uma ferramenta universal (como o execute_typescript). O modelo de linguagem passa a atuar como um compilador e sintetizador de programas, escrevendo rotinas consolidadas em linguagens de altíssima representatividade em seus dados de treinamento (como TypeScript ou JavaScript).TypeScriptimport { fetchCustomerOrders, calculateRiskScore } from 'virtual:tools';

export async function runAgentWorkflow() {
  const orders = await fetchCustomerOrders({ customerId: 'cust_8921' });
  const highValueOrders = orders.filter(o => o.amount > 10000);

  const results = await Promise.all(
    highValueOrders.map(async (order) => {
      const score = await calculateRiskScore({ orderId: order.id });
      return { orderId: order.id, score, status: score > 0.75 ? 'FLAGGED' : 'CLEARED' };
    })
  );

  return results.filter(r => r.status === 'FLAGGED');
}
O impacto econômico e computacional dessa mudança é profundo. A compressão de contexto ocorre porque dados brutos intermediários — que antes precisavam passar pela rede neural do LLM para que o modelo decidisse o próximo passo — permanecem confinados na memória do runtime. Testes empíricos demonstram uma redução de uso de tokens da ordem de 32% em tarefas simples e até 81% em operações em lote de alta complexidade. Em sistemas de larga escala com milhares de rotinas (como APIs corporativas completas), abordagens baseadas em busca e execução programática reduzem a carga de contexto do servidor de MCP de 1,17 milhão de tokens para menos de 1.000 tokens — uma eficiência de compressão de 99,9%.Matematicamente, a economia de tokens de entrada $\Delta_{tokens}$ em um fluxo de $N$ chamadas de ferramentas pode ser formulada como:$$\Delta_{tokens} = \sum_{i=1}^{N} \left( C_{prompt, i} + C_{payload, i} \right) - \left( C_{code\_prompt} + C_{final\_result} \right)$$Onde $C_{payload, i}$ representa os dados brutos retornados pela ferramenta $i$ que deixam de ser serializados na janela de contexto. Paralelamente, a latência total $T_{total}$ transiciona de uma complexidade linear dependente do tempo de inferência do modelo $\mathcal{O}(N \cdot (t_{llm} + t_{net}))$ para uma latência quase constante $\mathcal{O}(1 \cdot t_{llm} + t_{sandbox\_exec})$, na qual $N$ chamadas I/O são paralelizadas nativamente no runtime através de concorrência baseada em promessas (Promise.all).Dimensão de AnáliseJSON Function Calling (Padrão)Model Context Protocol (MCP Declarativo)Code Mode ProgramáticoMecânica de ExecuçãoChamadas de ferramentas atômicas e sequenciais mediadas pelo modelo.Invocação de ferramentas via cliente/servidor baseada em JSON-RPC.Geração de script compilável emitido em 1 turno de inferência.Custo de TokensAlto ($\mathcal{O}(N)$ re-injeções de schemas e payloads intermediários).Médio-Alto (exposição massiva de schemas no contexto).Mínimo (redução de 32% a 81% e até 99,9% em grandes APIs).Latência por TurnoElevada ($N$ round-trips sequenciais via inferência de LLM).Elevada ($N$ round-trips de rede mais inferência).Determinística e reduzida ($1$ turno de inferência + execução paralela local).Complexidade de EstadoO estado do fluxo deve ser serializado na janela de conversa.O estado reside no histórico do agente ou no servidor MCP.O estado é mantido em memória no isolate/sandbox durante a execução.Flexibilidade & LógicaLimitada a decisões condicionais simples entre turnos do LLM.Restrita à interface exposta pelos servidores MCP.Completa (suporte nativo a loops, condicionais, estruturas de dados e AST).Precisão ComputacionalPropensa a erros estatísticos em cálculos e agregações.Dependente das ferramentas de cálculo expostas.Exata (operações matemáticas e de agregação delegadas ao motor JS).2. Framework de Design de Código para Aderência de LLMsA eficácia do paradigma Code Mode é condicionada pela arquitetura das bibliotecas e interfaces expostas ao modelo. LLMs de fronteira exibem aderência desproporcionalmente superior ao código TypeScript quando comparado a esquemas estruturados ad-hoc, devido à predominância de repositórios de código real em seus dados de pré-treinamento. No entanto, ambiguidades sintáticas, aninhamentos profundos e sistemas de tipos mal projetados induzem alucinações de importação e métodos inexistentes.Estratégias Estruturais de Bibliotecas e Ergonomia de APIsPara otimizar a síntese de código pelo LLM sem contaminar o espaço de nomes (namespace), o design da SDK deve seguir o padrão Functional Core / Imperative Shell associado a namespaces planos (flat namespaces).A adoção de namespaces planos (como users.getInvoice()) em detrimento de estruturas profundamente aninhadas (como client.services.v1.users.billing.getInvoice()) reduz sensivelmente a taxa de erro de autocompletar e inferência do modelo. Da mesma forma, as ferramentas expostas devem aceitar um único objeto de opções tipado como parâmetro principal (por exemplo, fn({ id, limit })), eliminando a vulnerabilidade a erros de ordenação de argumentos posicionais.A injeção dinâmica de módulos mockados (import { weather } from 'virtual:tools') ou a presença de stubs declarados no escopo global do isolate garante que o autocompletar e a geração do LLM não falhem devido a rotas de importação estáticas inexistentes no ambiente de execução.Sistemas de Tipagem e Injeção de Definições de Ambiente (Ambient Types)A precisão da inferência zero-shot é severamente amplificada pela inclusão de declarações de tipos rigorosas (.d.ts) com documentação estruturada via JSDoc. Para evitar sobrecarregar a janela de contexto com arquivos .d.ts gigantescos de bibliotecas de terceiros, aplica-se a Injeção Dinâmica de Tipos Sob Demanda (Dynamic Ambient Type Injection). Um serviço de introspecção analisa a intenção da requisição do usuário, seleciona os schemas necessários e compila uma declaração de ambiente concisa, que é injetada no bloco de instrução de sistema (System Prompt), permitindo que o LLM veja exatamente as interfaces disponíveis e seus tipos associados.Protocolo de Autocorreção Guiado por Feedback (Self-Debugging Loops)Mesmo com declarações de tipo estritas, a geração de código está sujeita a falhas sintáticas ou erros de execução em tempo de runtime. O Code Mode viabiliza o encerramento de ciclos de feedback autônomos (Self-Debugging Loops) locais antes que uma resposta errônea seja entregue ao orquestrador principal.O protocolo operacional de autocorreção desdobra-se em um fluxo contínuo de quatro fases interligadas:Compilação e Linter Dinâmico (Fase Estática): Antes da execução, o script gerado passa por um analisador léxico/sintático ultrarrápido (como oxc ou swc em WASM). Se houver violação de sintaxe ou ausência de variáveis declaradas, o erro de compilação é capturado instantaneamente.Execução Protegida (Fase Dinâmica): Se o linter aprovar o código, o script é executado no Isolate Driver. Caso ocorra uma exceção de runtime (como um TypeError por propriedade indefinida), o runtime captura a Stack Trace completa, juntamente com os tipos dos parâmetros de entrada.Injeção de Diagnóstico no Contexto: O erro estático ou a exceção de runtime é formatado estruturadamente e re-injetado na conversa com o LLM, acompanhado da indicação exata da linha e coluna da falha.Reflexão e Re-inferência em Loop Fechado: O LLM processa o erro retornado, realiza a correção sintática ou lógica e emite um novo script corrigido em um sub-loop local, sem expor a falha intermediária ao usuário final.3. Blueprint de Engenharia de Infraestrutura e SandboxingA execução de código gerado por LLMs exige uma infraestrutura de sandboxing que equilibre tempo de inicialização (cold start), consumo de memória, desempenho computacional e isolamento de segurança absoluto.Arquitetura em Camadas do Runtime de AgentesA infraestrutura normativa para a execução segura de scripts de agentes é dividida em quatro camadas de isolamento e governança:A Camada de Orquestração (Host Agent Layer) é responsável por gerenciar a sessão do usuário, manter o histórico de mensagens, converter ferramentas MCP em definições TypeScript e submeter a chamada execute_typescript ao driver de isolamento.A Camada de Isolamento (Isolate Driver Layer) estabelece a abstração operacional implementada via interface padronizada (como o IsolateDriver do TanStack AI), garantindo que o motor subjacente possa ser alterado de forma transparente entre nós da infraestrutura.A Camada de Governança de Recursos e Limites monitora ativamente o consumo de tempo de CPU, a alocação de heap de memória e as restrições de E/S. Por fim, a Camada de Segurança e Proxy de Rede intercepta e filtra qualquer tentativa de comunicação de rede de saída ou introspecção de sistema não autorizada.Matriz de Decisão de Runtimes de SandboxingA escolha do driver de runtime correto determina a densidade de instâncias por servidor e o nível de proteção contra ataques de interrupção ou escape de sandbox.Driver de RuntimeTecnologia SubjacenteCold Start LatencyMemory Footprint / InstânciaDesempenho (Throughput)Dependências NativasIsolamento de SegurançaNode V8 Isolate (ex.: @tanstack/ai-isolate-node via isolated-vm)Isolados V8 compartilhando o mesmo processo C++.~1ms - 5ms~2MB - 10MBMuito Alto (V8 JIT Compiler)Sim (Módulos C++ / Node-gyp)Médio-Alto (Requer atenção contra Spectre/Side-channel).QuickJS WASM (ex.: @tanstack/ai-isolate-quickjs)Motor QuickJS compilado para WebAssembly.< 1ms~1MB - 3MBBaixo-Médio (Interpretador puro)Nenhum (Portabilidade Universal / Edge / Browser)Altíssimo (Isolamento por Sandbox da memória WebAssembly)QuickJS Bun FFI[cite: 9]QuickJS nativo vinculado via bun:ffi.< 1ms~2MB - 5MBMédioDepende do runtime Bun.AltoDynamic Workers / Cloudflare Edge[cite: 7, 13]Isolados V8 nativos na borda da rede (Edge).~5ms - 15ms~5MB - 15MBAlto (V8 JIT)Nenhuma (Gerenciado pela infraestrutura)Altíssimo (Isolamento de infraestrutura multitenant).MicroVMs / Containers (Firecracker / gVisor / Daytona)Virtualização de hardware leve ou interceptação de chamadas de sistema.100ms - 500ms128MB - 512MBNativo de Sistema OperacionalRequer suporte KVM / Docker no HostMáximo (Kernel Linux isolado)Governança de Recursos e Mitigação do Problema da Parada (Halting Problem)Executar código arbitrária ou autonomamente sintetizado introduz o risco de loops infinitos (while(true) {}) e ataques de negação de serviço por exaustão de memória. A cada instrução ou salto executado pelo script, um contador decrementa um valor $F_{initial}$. Isolamento Criptográfico, de Dados e Segurança de RedesA prevenção contra exfiltração de dados e injeção lateral de instruções (Indirect Prompt Injection) exige um modelo de segurança baseado na premissa de Zero Trust no Código Gerado:A eliminação completa do acesso ao ambiente do sistema hospedeiro exige que objetos como process.env ou globalThis.process sejam removidos do contexto do isolado. Segredos de API não devem ser expostos diretamente ao código gerado; a SDK intermediária realiza a subscrição e a injeção de autenticação em uma camada opaca gerenciada pelo host.Qualquer chamada de rede originada dentro do sandbox deve passar obrigatoriamente por um proxy transparente de auditoria com lista de permissões (whitelisting) de domínios estritamente autorizados. Domínios arbitrários ou conexões em portas não padronizadas são bloqueados no nível de socket. Além disso, runtimes baseados em V8 Isolate implementam defesas contra ataques de canal lateral (Spectre mitigations), impedindo que o script meça tempos de acesso a memória de alta precisão via performance.now().4. Arquitetura do Subsistema de Skills e Persistência de CódigoUma limitação fundamental de agentes tradicionais é a incapacidade de acumular aprendizado operacional: o sistema resolve um problema complexo gerando código, mas descarta a solução ao término do turno, sendo forçado a despender recursos para resolver o mesmo problema no futuro. O subsistema de Skills Persistentes (como o @tanstack/ai-code-mode-skills) resolve esse dilema transformando scripts bem-sucedidos em ativos operacionais reutilizáveis e fortemente tipados.Ciclo de Vida Formal de uma Habilidade (Skill Graduation)A transição de um script descartável para um módulo confiável em produção obedece a um fluxo rigoroso de promoção baseado em métricas de execução estocástica:Script Efêmero (Ephemeral Code): O LLM sintetiza um script em resposta a uma solicitação pontual do usuário. Se a execução for bem-sucedida, o código é capturado para análise de reutilização.Estágio Provisório (Provisional Skill): O script aprovado sem exceções é registrado no repositório de habilidades com o status Provisional. O critério padrão para atingir e manter esse estágio exige um histórico acumulado de pelo menos 10 execuções com uma taxa de sucesso mínima de 90% ($\ge 90\%$).Estágio Confiável (Trusted Skill): À medida que o agente reutiliza o script para requisições com objetivos equivalentes, a telemetria monitora sua estabilidade. Ao atingir o limiar de 100 execuções com taxa de sucesso igual ou superior a 95% ($\ge 95\%$), a habilidade avança para o status Trusted.Graduação a Ferramenta Nativa (Tool Graduation): Uma habilidade declarada como Trusted tem sua assinatura exposta permanentemente na lista de stubs de ferramentas primárias do sistema. Futuras requisições deixam de solicitar a geração de novos scripts do zero, invocando diretamente a habilidade graduada via chamada otimizada.Composabilidade Espaço-Temporal no DeepSeek Harness e CordisO ecossistema DeepSeek Harness (dsh) expande a flexibilidade arquitetural de agentes ao fundamentar-se no framework Cordis (formalizado no trabalho acadêmico "A Programming Paradigm for Spatiotemporal Composability").Enquanto runtimes convencionais tratam ferramentas e adapters de LLM como entidades estáticas registradas na inicialização do servidor, o Cordis formaliza o conceito de Composabilidade Espaço-Temporal:A Composabilidade Temporal (Temporal Composability) representa a capacidade do runtime de reverter totalmente os efeitos colaterais de um componente (revertible effects) no instante em que ele é desinstalado ou desativado, sem necessitar da reinicialização do processo servidor. Quando um plugin injeta ferramentas no contexto, subscreve a eventos e inicia temporizadores, sua remoção limpa rigorosamente todas as referências residuais na memória.A Composabilidade Espacial (Spatial Composability) expressa a capacidade de um componente declarar declarativamente suas dependências (reactive coeffects) e reagir dinamicamente a alterações no grafo do sistema. Se o provedor de inferência (adapter LLM) for alternado entre provedores em tempo de execução, todas as ferramentas e loops agênticos vinculados reajustam suas rotas de tradução de chamadas instantaneamente.No DeepSeek Harness, o próprio loop agêntico principal é estruturado como um plugin desacoplado. Essa escolha permite a substituição a quente (Hot Module Replacement - HMR) da lógica do agente, do sistema de sandboxing ou do registro de habilidades em tempo real sem interrupção do serviço.Indexação Semântica e Registro AST de SkillsPara evitar o inchaço da janela de contexto ao acumular dezenas de habilidades graduadas, o repositório de habilidades adota uma estratégia de indexação híbrida de duas camadas:Camada de Indexação Semântica (Vector Registry): A descrição textual em linguagem natural e os casos de uso da habilidade são convertidos em vetores de embedding. Durante a fase de preparação do contexto, realiza-se uma busca por similaridade de cosseno com a intenção do usuário, injetando no prompt apenas os tipos das 3 a 5 habilidades mais relevantes.Camada de Verificação Estrutural (AST Registry): Cada habilidade armazenada é mapeada por um hash SHA-256 de sua Árvore de Sintaxe Abstrata (AST) desprovida de comentários e nomes de variáveis locais. Quando o LLM tenta emitir um novo script, o runtime calcula o hash AST da solução gerada; se houver correspondência exata com uma skill confiável preexistente, a execução é delegada à versão pré-compilada do repositório.5. Guia Normativo de Diretrizes de Engenharia (Checklist Acionável)Equipes de engenharia de software e arquitetura de sistemas que pretendam implementar uma infraestrutura corporativa de agentes baseada em Code Mode devem validar rigorosamente os requisitos operacionais listados a seguir:A. Design de SDK e Interfaces de Tipagem[ ] Achatamento de Namespaces: Expor stubs de ferramentas em APIs planas de nível único ou no escopo global do isolate, evitando acoplamentos com o sistema de arquivos estático.[ ] Tipagem Estrita com .d.ts: Injetar declarações TypeScript com anotações JSDoc abrangentes no bloco de contexto de sistema (System Prompt) do modelo.[ ] Garantia de Parâmetro Único: Projetar todas as funções para aceitarem um único argumento do tipo objeto contendo opções tipadas, evitando erros de ordenação de argumentos por inferência.[ ] Tratamento Estático de Tipos: Garantir que o ambiente de compilação remova anotações de tipo TypeScript antes da execução no motor JavaScript do sandbox.B. Infraestrutura de Runtime e Sandboxing[ ] Seleção Criteriosa do Driver (IsolateDriver): Adotar V8 Isolates (@tanstack/ai-isolate-node / Dynamic Workers) para cenários que exijam máxima performance JIT, ou QuickJS WASM (@tanstack/ai-isolate-quickjs) para portabilidade universal sem dependências C++ nativas.[ ] Imposição de Limitadores Financeiros e de Recursos: Configurar limites estritos de tempo de execução de CPU (ex.: 5000ms) e teto de heap de memória em tempo de instanciação do isolado (ex.: 128MB).[ ] Instrumentação de Prevenção do Problema da Parada: Implementar fuel consumption em motores WASM ou transformações AST para injeção automática de contadores de iteração em loops for/while.[ ] Isolamento de Processo Hospedeiro: Assegurar que os objetos process.env, globalThis.fetch não autorizado e bibliotecas de acesso ao sistema de arquivos do servidor host estejam inacessíveis no sandbox.C. Segurança, Conectividade e Governança[ ] Proxy de Rede Transparente: Rotear todo o tráfego de saída do sandbox por um proxy de auditoria com lista de permissões (whitelisting) de domínios explicitamente autorizados.[ ] Injeção Transparente de Credenciais: Tratar tokens de autenticação de APIs corporativas na camada de infraestrutura do host, sem nunca expor segredos criptográficos ou variáveis de ambiente diretamente ao código gerado pelo LLM.[ ] Auditoria de Integridade de AST: Implementar validação sintática estática (Linter) no código emitido antes da execução dinâmica no runtime de sandboxing.D. Ciclo de Vida de Skills e Telemetria[ ] Implementação de Ciclo de Graduação: Configurar regras automáticas de promoção de scripts efêmeros baseadas em limiares de volume de execução e taxa de erro (ex.: Provisional aos 10 acertos a 90%; Trusted aos 100 acertos a 95%).[ ] Busca Híbrida de Habilidades: Armazenar skills em um repositório indexado por similaridade vetorial (para seleção semântica) e por hash AST (para deduplicação exata de rotinas executáveis).[ ] Monitoramento OpenTelemetry / AG-UI Protocol: Instrumentar a telemetria do loop agêntico transmitindo eventos estruturados de geração de código, tempo de compilação, tempo de sandbox e resultados estruturados diretamente à interface de usuário e dashboards de observabilidade.
