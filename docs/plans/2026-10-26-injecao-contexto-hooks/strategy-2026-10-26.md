# Interruptor de injeção de contexto — desenho e uso

> Complemento de `analysis-2026-10-26.md` (a medição e o veredito). Aqui: o desenho,
> a cobertura, o custo e o modo de uso.

---

## 1. A chave

```bash
TOURING_HOOK_INJECTION = full | no-advisory | off
```

| nível | o que faz | quem deve usar |
|---|---|---|
| **`full`** (padrão) | nada muda. Caminho idêntico ao de hoje: o shim faz `exec` direto, sem processo extra e sem mudança de latência | quem quer o comportamento atual |
| **`no-advisory`** | suprime as famílias de **sermão** (`touring-suggest`, `prompt-enhance`, `plugin-hook`, `post-tool-echo`, `raw-stdout`). **Mantém** o enriquecimento (blast radius, file context, syntax pre-check, loop_resume) e **mantém** todos os gates, inclusive o payload do code-mode-deny | quem acha a injeção barulhenta mas não quer perder o conhecimento do repositório nem a remediação dos gates |
| **`off`** | suprime **todo** o contexto injetado. Os hooks **continuam bloqueando** — `permissionDecision`, `decision`, `reason` e o exit code atravessam intactos | quem quer medir o baseline sem injeção, ou usa um modelo que já tem o contexto |

**Resolução**: variável de ambiente. Precedência: `TOURING_HOOK_INJECTION` > default `full`.
Valor inválido cai em `full` (fail-open: um valor mal digitado não apaga a injeção sem querer).

### Como ligar

**Por sessão** (export antes de abrir o Claude Code):

```bash
TOURING_HOOK_INJECTION=no-advisory claude
```

**Persistente** — o bloco `env` do `~/.claude/settings.json` (que já existe e já é o
lugar onde vivem `TOURING_PILLAR_INDUCTION_ARMED` e `TOURING_HOOK_TRACE_FILE`):

```json
{ "env": { "TOURING_HOOK_INJECTION": "no-advisory" } }
```

> O `settings.json` é configuração do usuário e **não foi alterado** nesta rodada:
> a mudança de comportamento global do harness é decisão do Gabriel
> (gate humano de `settings.json`, ver loop-engineering §Human-in-the-loop).

### Como desligar de volta

Remover a variável (ou pôr `full`). Não há estado persistido: o interruptor é
avaliado a cada invocação de hook.

## 2. A separação que sustenta o desenho

O protocolo de hook do Claude Code tem **dois canais**:

| canal | campos | efeito |
|---|---|---|
| **contexto** | `hookSpecificOutput.additionalContext`, `additionalContext` na raiz, `systemMessage` | entra na janela do modelo |
| **decisão** | `permissionDecision`, `permissionDecisionReason`, `decision`, `reason`, `continue`, exit code | bloqueia / libera / interrompe |

**FACT [1.0]** — no corpus de 1.028 sessões, **34 combinações de hook bloqueiam sem
injetar um byte** (`inj_bytes = 0`): `touring-quality` BLOCK dims, `Git guard`,
`config_protection.py`, `touring-process-guard.sh`, `loop_outer_effect.py`,
`loop_stop_guard.py`, `agent_model_gate.py`, `fable_consent_guard.sh`.

O interruptor toca **só o canal de contexto**. Por isso desligar a injeção não
degrada o enforcement — e isso foi provado, não afirmado (ver §5).

**Verificado no código** (não inferido):

| função | campos que escreve | file:line |
|---|---|---|
| `deny_response` | `permissionDecision: "deny"` + `permissionDecisionReason` — **zero `additionalContext`** | `crates/touring-cli/src/cli_suggester.rs:5426-5435` |
| `advisory_response` | `additionalContext` — **zero `permissionDecision`** | `crates/touring-cli/src/cli_suggester.rs:4176-4184` |

**Limitação conhecida**: `crates/touring-hook-runtime/src/verdict.rs:27` (`deny_reason_with`)
**cola os avisos dentro do `permissionDecisionReason`** (marcador `[também, sem bloquear]`).
Sob `off`, esses avisos ainda chegam ao modelo — junto do deny. O corte exige agir ali, em Rust,
sem tocar a razão original. Está na Wave 2 (§6.3).

## 3. Onde o interruptor mora (a cobertura)

### 3.1 Lado Rust — o shim

`scripts/hooks/touring-hook-shim.sh` (fonte versionada; instalado em
`~/.claude/hooks/touring-hook` por `scripts/update-touring`, linha 308).

O shim resolve o binário por 4 camadas (FORCE_BIN → walk-up per-project →
toolchain do usuário → fallback global) e hoje faz `exec` direto nos 4 pontos.
A mudança troca cada `exec` por `run_touring_hook`, que:

- em `full`: faz o mesmo `exec` de antes (caminho **byte-idêntico**, zero overhead);
- em `no-advisory`/`off`: captura o stdout, passa pelo filtro e reemite,
  **preservando o exit code** e o stderr.

Todos os hooks Rust (`cli-suggest`, `pre-read`, `pre-edit`, `pre-write`,
`prompt-enhance`, `session-start`, `post-*`, `ceg-observe`, …) passam por ali:
**~95% dos bytes injetados do corpus**.

### 3.2 Lado Python/shell — o guard no próprio hook

`client/hooks/injection_policy.py` é a fonte única da verdade: resolve o nível,
classifica a família do payload e decide. Cada hook advisory consulta antes de
emitir:

```python
import injection_policy
if not injection_policy.allows("plugin-hook"):
    return 0
```

Hooks em shell usam a interface de CLI:

```bash
if ! python3 "$HOME/.claude/hooks/injection_policy.py" --allows post-tool-echo >/dev/null 2>&1; then
    exit 0
fi
```

### 3.3 A guarda de conformidade

`scripts/guard_injection_policy.py` enumera os **152 registros de hook** de
`~/.claude/settings.json` (25 eventos), classifica cada um e reprova quando um
injetor não consulta a política.

```
python3 scripts/guard_injection_policy.py
```

**Cobertura verificada em 26/10/2026: 152/152 registros cobertos.**
(E 134 combinações injetoras distintas no corpus; 18 são inertes ou de
enforcement.)

Sem essa guarda, o interruptor mentiria: um injetor novo nasceria fora do
controle e o silêncio apareceria como "funcionou". É a mesma doutrina de
`touring-4-pillars.md`: *enforcement mora no executor, não no anúncio*.

## 4. O custo do interruptor

| nível | custo | observação |
|---|---|---|
| `full` | **zero** | `exec` direto; nenhum processo extra |
| `no-advisory`/`off` | 1 processo `python3` por invocação de hook | ~15–25 ms por hook; a mediana do hook é 60–430 ms, então o custo é da ordem do ruído |

O custo só existe quando o interruptor está fora de `full` — que é a decisão de
quem o liga.

**Se o filtro falhar** (python ausente, arquivo corrompido), a saída original
passa **inteira**, com um aviso em stderr. A escolha é deliberada: perder um
`deny` é risco de segurança; deixar de suprimir contexto é custo, não risco.

## 6. Onde isto se liga ao resto (e o que NÃO está feito)

### 6.1 A régua precisa de dois emojis novos

`touring kpi -j` → `context_budget` já existe e já reprova
(`injected_bytes_per_turn = 2.757` contra teto 2.000; `injection_follow_ratio = 0,5`
contra piso 0,6). Mas a régua mede **proposições** (ações propostas), não **fatos**
(informação sobre o código) — e o valor do Touring está nos fatos. E a amostra
dela é de 3 transcripts / 6 MUSTs, enquanto a medição de corpus com 6.000 MUSTs
dá follow-ratio **0,094**.

Wave 2 da régua: `fact_kb` (bytes de conhecimento único por família) e
`nudge_follow_ratio` (follow-ratio do canal de permissão, sobre a população).

### 6.2 O orçamento por turno já existe e não amarra

`crates/touring-hooks-shared/src/turn_budget.rs` implementa o acumulador por
turno (S-3.3 do plano `economia-de-contexto`), com `TOURING_TURN_BUDGET` como
ajuste. O próprio docstring diz: o teto foi calibrado em **12,4% da mediana do
turno** — ou seja, **aceita** o turno gastando 16 KB e corta só 2 KB. E ele
governa **apenas** a família `cli-suggest`.

O interruptor é a alavanca que faltava: ele atua sobre **todas** as famílias, e
distingue o canal de fato do canal de sermão, coisa que um orçamento por
volume não distingue.

### 6.3 Wave 2 — o que fica

| item | por quê | esforço |
|---|---|---|
| Implementação **nativa em Rust** em `crates/touring-hooks/src/main.rs:687-699`, dentro de `forward_daemon_output` (`:670-709`) | é o **único** ponto de impressão do caminho daemon, e **já é um pós-processador JSON no wire** (`parse → stamp_invoking_event → split_off_invoking_event_violations → re-serialize`). O predicado entra ali como mais um filtro, e ali alcança também `systemMessage` — que o shim não alcança (o `systemMessage` é canal de usuário, não de modelo) | build release do workspace + `update-touring` |
| Cortar os avisos **colados dentro do `permissionDecisionReason`** | `crates/touring-hook-runtime/src/verdict.rs:27` (`deny_reason_with`) cola os avisos no reason com o marcador `[também, sem bloquear]`. Sob `off`, esses avisos ainda chegam ao modelo. O corte tem de agir ali, **sem tocar** a razão original do deny | médio |
| `touring pre-task-scout` (roda pelo CLI, não pelo shim) | 5,6 KB em 21 dias — irrelevante no volume, mas é lacuna de cobertura | baixo |
| Guardar `post_quality_gate.py` (stdout de depuração cru, 5,3 MB = 9% da injeção) | não é hook do Touring (é do projeto), mas é o maior ruído isolado do corpus | médio |
| Emitir o nível da política em `touring kpi -j` | para que a régua diga sob qual política foi medida | baixo |

> **Achado de A1 (verificado)**: `cli_suggest` é **silencioso no caminho standalone** —
> `crates/touring-hooks/src/main.rs:268-271` faz `let _ = touring_hooks::cli_suggester::run(...)`
> e descarta o retorno. O suggester (61% da injeção) só produz saída pelo daemon, o que confirma
> `daemon.rs:623` e `main.rs:670` como o mesmo nó lógico para essa família — e o filtro no shim
> a alcança, porque o shim repassa a saída do daemon.

## 6.4 A semântica exata, por nível

Verificado por `scripts/test_injection_policy.py` (36 asserções) e pela prova em hook real:

| conteúdo do payload | `full` | `no-advisory` | `off` |
|---|---|---|---|
| **fato** do repositório (blast radius, file context, syntax pre-check) | passa | **passa** | sai |
| **sermão** (`[TOURING SUGGEST]`, prompt-enhance, plugin-hook, eco de pós-tool) | passa | **sai** | sai |
| **log de depuração cru** (`[EVENT_READER]…`) | passa | **sai** | sai |
| **payload desconhecido** (sem marcador reconhecível) | passa | **passa** (conservador) | sai |
| `permissionDecision` / `permissionDecisionReason` / `decision` / `reason` / exit code | passa | **passa** | **passa** |

**Por que "conservador" no desconhecido**: `verdict.rs:37` (`context_with`) compõe os avisos
primeiro e o contexto do veredito depois, num texto só. Julgar o payload inteiro pela família
primária descartaria o fato que veio de carona. Por isso `no-advisory` só suprime o que é
**exclusivamente** sermão — e o log de depuração, que é 9% da injeção, tem marcador próprio
(`debug-stdout`).

---

## 7. A tese, em uma frase

> **A injeção ajuda quando carrega um fato; atrapalha quando carrega um sermão.**
> O corpus mediu 27,8% da janela em injeção — mas ~44% dela é conhecimento do
> repositório (95–97% único) e ~56% é persuasão, repetição e log de depuração.
> O interruptor não é "desligar a injeção": é **separar o fato do sermão**,
> mantendo o enforcement — que é o único canal que medidamente mudou o
> comportamento do modelo nesta sessão.
